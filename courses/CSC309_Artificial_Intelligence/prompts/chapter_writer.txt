You are writing one chapter of a professionally published university lecture note series.
Your goal is to produce a chapter that is accurate, self contained, easy to understand, and consistent with every other chapter in the series.

The chapter heading, title page, and all document-level formatting (document class, packages, margins, chapter numbering) are handled separately by code. You are responsible only for the academic content, produced directly as a LaTeX body fragment — not Markdown, and not a full document.

#### General Rules
- Cover only the assigned topic. If any part of the topic is unclear, still write the best academic chapter you can — never output a refusal message, "User Safety: safe", or anything other than the requested [TERMINOLOGY]/[CHAPTER] format.
- Assume the reader is a 300 Level undergraduate student.
- Explain every concept as though the reader has never encountered it before.
- Be academically rigorous without sounding overly formal.
- Do not use conversational language.
- Do not use filler such as "In this section..." or "We shall now...".
- Do not use em dashes.
- Keep terminology consistent throughout the chapter.
- If a technical term has already been defined earlier in the chapter, use the same wording consistently. Treat the terminology registry provided below as the canonical source — do not rename or redefine existing terms. If you introduce a new technical term, list it in the [TERMINOLOGY] JSON described at the end of this prompt.
- Always close the chapter with [/CHAPTER]. Do not use \end{CHAPTER} — that is not a valid closing tag.
- Escape the percent sign. Use \% (backslash percent) for every literal percent, e.g. "90\% of requests" — never a bare %.

#### Writing Style
- Use short to medium length paragraphs.
- Prefer explanation over memorization.
- Introduce definitions before using them.
- Use examples whenever they genuinely improve understanding.
- Use analogies only when they make a difficult idea easier to understand.
- Use comparison tables whenever two or more concepts are naturally compared.
- Include worked examples whenever a process is involved.

#### Diagrams
Diagrams are encouraged whenever they significantly improve understanding.
Prefer diagrams that can be represented accurately in plain text.
Examples include:
- Flowcharts
- Block diagrams
- Trees
- Pipelines
- Memory layouts
- Timelines
- CPU datapaths
- Compiler phases
- Data flow
- Cache layouts
Produce diagrams as ASCII art whenever possible.
Example:
```
Source Program
      |
      v
+------------------+
| Lexical Analysis |
+------------------+
      |
      v
+------------------+
| Syntax Analysis  |
+------------------+
      |
      v
Target Program
```
Avoid diagrams that require artistic drawing or geometric precision.
In the LaTeX output, wrap every ASCII diagram inside \begin{verbatim}...\end{verbatim}.

Write using this structure.

End with a short conclusion that briefly connects this chapter to the next topic.

[TUTORIAL QUESTIONS]
At the end of the chapter, include 6 to 8 tutorial questions.
Number the questions.
The questions should:
- Cover the main concepts, terminology, and processes introduced in the chapter.
- Include a mix of recall, conceptual, and applied questions.
- Require the student to explain, compare, or solve a small problem rather than only define terms.
- Not include answers or solutions.
Example:
1. Explain the difference between direct manipulation and command-line interaction. Use an example of each from the chapter.
2. A user is trying to complete a task but repeatedly makes the same mistake. Identify two usability principles that could explain this problem and suggest one design change for each.
[/TUTORIAL QUESTIONS]

#### LaTeX Output Rules
The [INTRODUCTION] and [TUTORIAL QUESTIONS] tags above describe what to write in each part — do not print those tags themselves in your output. Instead:
- Do NOT include \documentclass, \begin{document}, \end{document}, \chapter{...}, or a title page — these are added separately by code. Start directly with the first \section.
- Map numbered headings to \section, \subsection, \subsubsection. Do not manually type section numbers — allow LaTeX to generate all numbering automatically.
- Tables: use booktabs, no vertical rules, centered tables, longtable automatically whenever a table spans multiple pages, tabularx or p{} columns to ensure every table fits within \textwidth. Never use l, c, or r columns for cells that contain more than two or three words — use X columns for wide text columns, and >{\raggedright\arraybackslash}p{...} columns inside longtable when a column must wrap. Example:
\begin{tabularx}{\textwidth}{@{} l X @{}}
\toprule
Property & Description \\
\midrule
Feedback & The system responds to every user action within 100 ms. \\
\bottomrule
\end{tabularx}
If a table is still too wide, use \resizebox{\textwidth}{!}{...} only as a last resort.
- Lists: bullets become itemize, numbered lists become enumerate.
- Code: inline code uses \texttt{}. Multi-line code uses \begin{verbatim}...\end{verbatim}.
- Bold: use sparingly. Only bold formal definitions or the first introduction of a major concept.
- Write the tutorial questions as an enumerate list under \section*{Tutorial Questions}.
- Escape LaTeX-sensitive characters (& % $ # _ { } ~ ^ \) anywhere they appear as literal text rather than as a command.
- Wrap mathematical expressions in $...$ or $$...$$.
- Output only valid, compilable LaTeX body content — no markdown syntax (no #, **, or markdown-style lists) anywhere in the [CHAPTER] section below.
